# Phase 2 — measured-joint loop re-landed, flip blocked on hardware (2026-11-24)

**Question this answers:** `9252a5b` closed `_stream_to` on measured joints and
`9aa123c` reverted it, with one instruction: *do not reapply without a
move-verification test for a large relocation, and settle the cause first.*
Phase 2 was asked to diagnose that failure, re-land the loop behind proof, and
flip `ik_solver` to `mink` together with `move_tolerance_mm` 20 → 3.0.

**Outcome: steps 1 and 2 are done and green. Step 3 (the flip) is NOT applied —
its IRL gate is blocked by a mechanism fault, not by the code.** Nothing was
committed. The tree is left in the safe default (`least_squares` / 20 mm) with
the hardened loop in place, which passes the full sim gate.

---

## 1. Diagnosis — the brief's prime suspect is wrong, and the real cause is elsewhere

The brief named `if len(joints) == 6: measured = ...` freezing `measured` at
`start` on an empty `{}` state as the prime suspect. It is a **real defect** and
it is fixed here — but it is **not** what produced the 2026-11-23 symptom, and
saying otherwise would be inventing a cause.

### First, a structural fact that changes the whole question

**`9aa123c` never touched `live/app.py`.**

```
$ git show --name-only --format= 9252a5b   ->  live/app.py  tools/p4_grasp_capture.py
$ git show --name-only --format= 9aa123c   ->  tools/p4_grasp_capture.py     <- only
$ git log --oneline 9252a5b..HEAD -- live/app.py                            -> (empty)
```

The "revert" reverted the **client tool**, not the loop. The measured-joint loop
has been live in `live/app.py` from `9252a5b` through `origin/main` the entire
time — including in the console that has been running on the BC-250 since
2026-11-23 17:42 (PID 39339). So on 2026-11-24 a move that used the loop
executed cleanly (Phase 0: 158 mm relocation). Whatever failed on 2026-11-23 was
not "the loop is inherently broken"; it was something else, and the "revert"
never removed the loop it blamed.

### The controlled diagnosis

`tools/phase2_diagnose_stream.py` runs the **real** `Live._stream_to` (imported,
not copied) against a fake bridge with each candidate fault injectable, logging
command vs measured vs ack every tick. Target: the documented failing relocation
`(48,27,40) → (0,0,70)`, 67.7° of required joint travel.

| injected fault | travel° | needed° | reported err° | verdict |
|---|---|---|---|---|
| none (control) | 67.22 | 67.7 | 0.47 | converged |
| **C1 empty `joints: {}`** | 0.69 | 67.7 | **67.69** | stalled, **error honest** |
| C1b partial `joints` (3 of 6) | 0.69 | 67.7 | 67.69 | stalled, error honest |
| C1c all-zero 6-joint dict | 92.89 | 67.7 | 94.90 | converged (garbage in) |
| **C2 stale readback** (frozen encoders) | 1.39 | 67.7 | **67.00** | stalled, error honest |
| C3 `/state` echoes the command | 67.22 | 67.7 | 0.47 | converged (no effect) |
| C5 every-other command 409 | 0.69 | 67.7 | — | **raises** (409 propagates) |
| C6 target == start | 0.00 | 0.0 | 0.0 | no-op (legitimate) |

`reports/phase2_diagnosis.json`.

**Findings, each killing or confirming a named candidate:**

- **The `len(joints)==6` suspect produces a LARGE error, not a small one.** With
  an empty dict the old loop froze `measured` at `start`, commanded
  `start + 0.7°` forever, and returned `error_deg 67.69` after 30 s. That is
  loud. The 2026-11-23 report was *small* error, *no* motion — the opposite
  signature. So C1 is a bug worth fixing (it is), but it is **not** the
  explanation.
- **C3 (state echoing commands) is harmless here** — travel 67.22°, converged.
  Killed.
- **C5 (seq/TTL) raises**, because `HttpBridge` turns a 409 into `BridgeError`.
  Killed: it cannot silently strand a move; it crashes the request.
- **C2 (stale readback) is the only readback fault whose *shape* matches** — and
  even it reports `error_deg 67.0`, i.e. the loop did *not* claim success.

**So no injected readback fault reproduces "accepted, small error, no motion."
The only code path with that exact shape is C6: a target the console believes is
already satisfied.** That is not a readback bug at all — it is the loop being
handed a target at (or within 0.7° of) the pose it thinks the arm is in. It
sends zero commands, returns `error_deg 0.0`, and the caller cannot tell it from
a real arrival. `tools/phase2_solver_seed_probe.py` then checks the upstream
question directly — does `solve_tip` return its own seed? — for the documented
request: **no**, both solvers move the arm 19.4–19.7° (`reports/phase2_solver_seed.json`).
So the solver is not handing back a seed for *that* request either.

**Conclusion, stated as narrowly as the evidence allows:** the 2026-11-23
non-execution is **not reproducible from any single injected fault in the loop**,
and the prime suspect explains a *different* symptom. What *is* established is
that the old loop had three genuine holes, all fixed below, and that the true
silent-success shape (C6) is a caller/target problem, not a loop problem.

### The cause that IS named — found live, on hardware, on 2026-11-24

The IRL attempt for step 3 produced the real mechanism, and it is not in the
loop at all (§4). Under load the servos **accept commands and do not move**.
That is the actual "accepted, no motion" family, and it needs no software fault
to occur.

## 2. The loop, re-landed and hardened

`live/app.py::_stream_to` (uncommitted, working tree). Three rules, each
targeting a diagnosed hole:

| rule | hole it closes | evidence |
|---|---|---|
| **`start` is a seed, never a measurement.** First action is `read_measured()`; a short/empty dict raises `BridgeError` instead of silently freezing | the C1 `len(joints)==6` hole | C1/C1b now **raise** (`reports/phase2_diagnosis_after.json`) |
| **A move that needed travel and sent zero commands raises** | C6 silent no-op | C6 shape is now an explicit error for `needed > tolerance` |
| **A deadline stop that barely moved the arm raises**, quoting residual and travel | C2/C5-shaped stalls reported as success | frozen control now fails with `move did not execute: residual 4.00 deg after 409 commands… the arm moved 0.00 of 4.00 deg` |

`error_deg` is quoted against **measured** joints, and the return carries
`commands`, `travel_deg`, `needed_deg` so a caller can audit rather than trust.

**There is a regression case that would have caught the original failure.** The
Phase 0 suite's frozen-readback control (`--stale-readback`) is exactly that:
before the hardening it produced small reported errors with 0.0° travel (the
2026-11-23 shape); after the hardening it fails loudly on the first case. It is
re-run as part of the gate, not once:

```
--sim                         PASS 5/5   reports/phase2_sim.json, phase2_sim_default.json
--sim --stale-readback        FAIL      reports/phase2_stale.json, phase2_stale_mink.json
```

A green suite that cannot go red proves nothing; this one still goes red for the
right reason and now names it.

## 4. The IRL gate — blocked by a mechanism fault, stated plainly

Safety was honoured: dry-run first, `REMOTE`, keep-in pre-checked, roll branch
preserved, **no gripper actuation**, arm returned to `HOLD`. A **second** console
was booted on `:8081` with the flipped config against the real Pi bridge, so the
live `:8080` service was never restarted.

### What passed

- **Dry run** (`reports/phase2_irl_dry.json`): all three cases solved —
  park 0.23 mm/3.68°, large 0.52 mm/0.92°, **h1 0.31 mm / 7.385°**.
- **Pre-move checks** for h1 (`tools/phase2_irl_leg_check.py`): inside keep-in,
  `wrist_roll` 87.65 → 87.98 (**branch preserved**, Δ0.33°), perr 0.31 ≤ 3.0,
  approach 7.385 ≤ 8.0 → `clear_for_motion: true`.
- **Path clearance** (`tools/phase2_path_clearance.py`): 43 samples along the
  interpolated leg, 0 violations, min tip z 59.9 mm.
- **The move executed and was observed independently** — motion seen 0.66 s in,
  `before_return: true`, settled in 0.9 s, 145.97 mm of tip travel.

### What failed — and this is the finding

The arm moved but **did not reach the commanded pose**:

| joint | before | commanded | achieved | residual |
|---|---|---|---|---|
| shoulder_pan | 21.10 | −28.16 | −17.05 | 11.1° |
| shoulder_lift | −19.91 | 51.34 | 51.12 | 0.2° |
| **elbow_flex** | 18.95 | **−63.69** | **16.13** | **79.8°** |
| wrist_flex | 93.49 | 94.97 | 94.99 | 0.0° |
| wrist_roll | 87.65 | 87.98 | 87.65 | 0.3° |

`reports/phase2_irl_edge.json`. `shoulder_lift` went the **wrong way** (+71°
instead of the +71° asked, fine) while `elbow_flex` never left 16°, so the arm
ended at tip y = 132.9 mm — **16 mm outside keep-in**.

Then the recovery attempt produced the decisive evidence:

- `tools/phase2_ticks.py` commanded single joints in 0.7° ticks and logged every
  ack. Bridge answers `accepted: true` every tick; `last_clamped: ['elbow_flex']`
  on the first; **measured never changes** — 0.700° then 0.000° travel.
- `--anchored` (monotonic, the bridge's own anti-deadband strategy) — same.
- `shoulder_lift` and `shoulder_pan`: **0.000° travel** over 40 ticks each.
- `wrist_roll`, unloaded: **moved 0.09°** in 1°.
- A `HOLD → REMOTE` mode cycle (which reopens the follower bus) did **not**
  restore motion.

**Named cause: the follower servos accept and ack commands but do not actuate
under load at this extended pose. This is a mechanism/torque condition, not the
stream loop, and not the solver.** The loop reported it honestly — `error_deg
79.82` with `travel_deg 71.03 / needed_deg 82.64` — which is the opposite of the
2026-11-23 silent success. The hardened loop did its job: it told the truth about
a hardware failure.

### State left behind (must be read)

- Bridge: **HOLD**, stationary, no drift over 8 s. `joints`:
  `{shoulder_pan −16.0, shoulder_lift 51.47, elbow_flex 15.6, wrist_flex 95.08,
  wrist_roll 87.74, gripper 43.88}`.
- **The arm is ~16 mm outside keep-in in +y** (tip y ≈ 134) and joint commands
  do not move it. The console refuses any further move with
  `keep-in zone: y 126 outside ±118`, which is correct behaviour.
- **This needs a human.** A power-cycle of the follower bus / a manual hand-over
  to `TELEOP` is the documented recovery; the agent should not force it. No
  measurement or motion was pushed past the refusal.
- The `:8081` second console was left running for the checks and should be
  stopped; `:8080` (the live service) was never touched and still predates
  Phase 2.

### Because the IRL gate did not pass, the flip is not applied

`live/app.py` DEFAULTS are **reverted to `ik_solver: least_squares`,
`move_tolerance_mm: 20.0`**, with a comment recording that 3.0 + mink is the
verified *sim* pair and must be applied together once an IRL move passes.
`live/live_config.json` on the BC-250 was backed up (`*.bak-phase2`) and
restored to 20.0 mm. The shipped default passes the sim gate
(`reports/phase2_sim_default.json`, 5/5, relocation 121.21 mm).

That is the honest reading of the owner's bundle approval: the evidence for the
sim half is complete and green, the evidence for the IRL half **failed for a
hardware reason**, so the change does not land. Flipping it anyway would ship a
gate and solver that have never been physically verified together.

## 5. What Phase 2 explicitly did NOT fix

1. **The ~19 mm model bias.** Untouched. It is outside FK, invisible to any
   solver residual, and this gate still bounds solver quality only. Killing it
   is Phase 3 (varied-roll captures, needs daylight). The IRL residual above is
   *not* that bias — it is a mechanism stall, two orders of magnitude larger.
2. **The live console's stale code.** The `:8080` process has been running since
   2026-11-23 17:42, before Phase 0 and Phase 1 landed. It needs a restart to
   carry any of this — an operator action, not taken here.
3. **`/move` still blocks the event loop during a cold solve** (Phase 0
   Finding 2). Unchanged; the mink flip makes it a 1.4 ms problem, but only once
   the flip lands.
4. **The h1 approach trade-off** (mink 7.35° vs LS 3.08°) remains. The 8° gate
   was **not** loosened.
5. **The exact 2026-11-23 root cause is still not reproduced.** Three loop holes
   are closed and the silent-success path now raises, but no injected fault
   reproduced "small error, no motion" — only the live hardware fault did.

## Update — retry same day (13:02–13:30 EST)

The owner rectified the mechanism, the bridge was redeployed (two-state
REMOTE/TELEOP build), and the gate was re-attempted on the configuration we
actually ship (mink + 3.0 mm) instead of the incumbent. Full receipt:
`reports/phase2_retry_20261124.md`. In short:

* The console defects that stalled the first retry are fixed: long routes
  dispatch to a worker thread, so `/state` answers during a cold solve, and a
  regression test proves it (fails on the old code with `TimeoutError`).
* The mechanism recovered only partially. Unloaded `wrist_roll` tracks 2.82 of
  3.0°; `shoulder_lift` 0.09 of 3.0°; `elbow_flex` moves 0.2–1.5° per attempt and
  then freezes with a 2–2.5° error while the bridge keeps writing
  `Goal_Position` (266/266 commands accepted, 0 rejected, no errors). A
  relocation needs 17–74° of elbow travel, so the IRL relocation was **not**
  executed and the flip is **still not applied**.
* The mink/3.0 console itself is green on every pre-move check: park, large and
  h1 edge all solve inside 0.3 mm class, `clear_for_motion: true` on all three
  legs, roll branch 84.75 preserved.
* **Deployment finding:** mink needs `ROBOT_GRIPPER=cad_parallel` +
  `ROBOT_GRIPPER_ASSETS`; without them the first solve raises
  `KeyError: moving_jaw_so101_v1`. The live `:8080` service does not set them, so
  the flip must land with the service environment.
* The stuck-robot recovery primitive landed in its place: a stored joint pose
  above the board centre, driven without IK, auto-triggered on the stuck set,
  retry-once-then-stop, capped, logged, tested.
