# Wrist camera focal length — measured from images, 2026-11-27

**Result: fx 838.5 px, fy 836.4 px (±1%). The calibration file is right. The 47.0°
constant used for rendering is not the lens — it is 1.51× off in focal length.**

Brian approved the measurement after the wide-volume solve showed a distance-versus-
focal-length signature. That hypothesis is now **disproven**: the focal length was
never wrong. The number that is wrong is the one the simulator renders with.

## Method — why this is independent

Zhang-style planar self-calibration (`cv2.calibrateCamera`) over the 23 wide3
captures, using the ChArUco marker grid as a plane of known *shape* in unit
squares. Homography orthogonality constraints fix the focal length without
knowing the board's metric size, its distance, the camera mount, or the arm
chain. No FK is used anywhere, so this cannot inherit the pose error.

700 corners over 21 views (every view with ≥4 markers), 640×480.

## Measurement — `reports/wide3_focal_20261127.json`

```
free 5-param (k1,k2,p1,p2,k3)   fx 838.5  fy 836.4  cx 337.4  cy 234.7  rms 1.31 px
zero tangential, k3 fixed       fx 834.8  fy 834.2  cx 312.1  cy 238.5  rms 1.32 px
seeded from calibration.json    fx 835.8  fy 835.2  cx 312.2  cy 238.5  rms 1.32 px
only f free, cx/cy/asp fixed    fx 848.0  fy 849.2  cx 320.0  cy 240.0  rms 1.33 px
```

Spread across the four parameterisations is under 1.6%, and every one lands on
rms ≈ 1.3 px. That is a tight, well-conditioned answer.

Comparison:

```
calibration.json    fx 831.9  fy 833.0  cx 320.0  cy 240.0   -> fovy 32.14 deg
self-calibrated     fx 838.5  fy 836.4                      -> fovy 32.02 deg
sim render constant WRIST_REFERENCE_FOVY_DEG = 47.0          -> f = 552 px (landscape)
ratio cal / render  1.51
```

So:

- `calibration.json` is confirmed to within 0.6–1.6%. Leave it alone.
- The principal point is the only loose term: 337 / 235 free versus 320 / 240
  stored, a 17 px shift in x. Worth a look eventually; it does not move f.
- `WRIST_REFERENCE_FOVY_DEG = 47.0` in `chess_sim/scene.py` describes the render
  camera, not the lens. It was fitted (`reports/sim_vs_irl_fovfit.json`) so the
  rendered marker side matched 95.6 px against 95.8 px IRL at the B5 reference
  pose. A render whose focal length is 1.51× the real one can only match image
  scale by sitting at a proportionally different distance — so the B5 reference
  camera pose and its render FOV are jointly wrong in a way that cancels for
  apparent size but not for perspective.

## The consequence for the mount question

With the focal length and the mount both pinned to their calibrated values, solve
the static board pose per view (`reports/wide3_boardspread_20261127.json`):

```
board t:  x -15.7 +- 14.0   y -35.3 +- 12.8   z 430.6 +- 6.3 mm
          (stored live/board.json: x -27.6  y -31.6  z 432.6)
rotation spread: median 1.64 deg   p90 5.97   max 9.39
board displacement across views: median 16.3 mm   p90 26.6   max 48.6
```

Two things fall out:

1. **Distance is right.** z solves to 430.6 ± 6.3 mm against a stored 432.6 mm.
   Nothing is scaling wrong. The joint fit's "mount −36 mm, board −33 mm" pairing
   was a free-parameter artifact of letting twelve unknowns chase 23 views, not a
   focal error. That reading is retracted.
2. **The remaining error is pose.** The board is a static object, so any per-view
   variation in its solved pose — 16 mm and 1.6° median, 49 mm and 9.4° worst —
   is the arm's pose model disagreeing with itself. That is the real remaining
   problem, and it is in the chain, not the camera.

## What to do about the render constant

Not changed here. Fixing it means setting the render FOV to the measured lens
(~32.0°) **and** moving the B5 reference camera to the true stand-off, then
re-checking the 95.8 px scale agreement and any frame pins that depend on the
rendered wrist image. Changing the FOV alone would make rendered markers 1.5×
too large. That is a deliberate sim-fidelity change with test consequences, so it
needs its own decision.
