## 1. The blocker, restated with evidence

`live/live_config.json` paired `layout_kind: charuco` with
`plan: chess_sim/assets/marker_scan_plan.json` — the **mat** plan
(`layout_offset_mm 152`, ids 0–3, tags 40 mm outside the board edge). Against
the printed face those poses look past the board.

Confirmed before changing anything: plan pose 0 saw ChArUco tags, poses 1–11 saw
none (`probe_plan2`), and `tools/plan_marker_scan.py` hard-coded
`fiducials.MarkerLayout.for_board(...)` with no ChArUco path.

## 2. Planner change

`tools/plan_marker_scan.py`:

- `--layout {mat,charuco}` (default `mat`, so nothing changes for mat work).
- `charuco` selects `CharucoLayout(square_mm=board.square*1000)`, ids **5–36**
  (derived from `charuco_face.square_of`, not a hard-coded range), the
  **playing-surface plane** (`marker_z = board.top` = 433.7 mm) and
  `layout_offset_mm = 0`.
- The scene is built with `board.face = "charuco"` for that mode. Without it the
  measured layout renders a wooden face and no ChArUco marker exists to plan
  against — the same trap that made the old scan tests unpassable.
- Candidates, coverage and the recovery table iterate the layout's own ids
  instead of the global 37-id set. For `--layout mat` that is
  `fiducials.GEOM_MARKER_IDS` (0–4): the old code walked all 37 and asked the
  mat layout for id 5, which raised `unknown marker id 5` — the same crash
  `observe_markers` and `object_points` already guard against. The mat path was
  broken before this block and is now merely incomplete (see §9).

`chess_sim/marker_scan.py` (production, additive):

- `MarkerScanPlan` gained an optional `marker_ids`, used by `views_per_marker`,
  `complete()` and `missing()`. Unset keeps the old behaviour (every id in the
  dictionary), so existing mat plans are untouched. A ChArUco plan that did not
  say so would report mat tags 0–4 as "missing" forever.
- `plan_from_observations(..., marker_ids=...)` and `save_plan`/`load_plan`
  round-trip it. Old plan files load unchanged.

## 3. Finding: the sim calibration did not match the sim camera

The first plan run used `reports/block3_sim_calibration.json`. Its plan looked
healthy in projection (8 poses, 75/75 placements covered, 19 ids per pose) but
**registered 0/7 placements**: "board solve failed with 28 markers".

Direct cause, measured against MuJoCo:

| | calibration says | MuJoCo `wrist` camera | delta |
|---|---|---|---|
| position | (0.0115, 0.1424, 0.6884) | (0.0140, 0.0980, 0.6937) | **44.4 mm in y** |
| rotation | — | — | **22.17°** |

Constant across poses, so it is the mount, not noise: `block3_sim_calibration`
was exported with a different gripper asset pack (`...-model.xml-...`) than the
scene the planner builds (`stock-jaw`). Reprojecting the true board pose gave
**116 px RMS** — no optimiser can fix a wrong camera model, and the plan's
`visible` sets were predictions from a phantom camera.

Fix: export the calibration **from the same scene**:

```fish
PYTHONPATH=. ~/.local/bin/robot-arm-sim python tools/export_wrist_calibration.py \
  --out reports/block4b_sim_calibration.json
# sim-1.15.0-stock-jaw-462.4mm-2026-11-15: 6 links, max position error 0.000000 mm
```

Truth reprojection then measured **0.59–0.79 px** per view at `marker_z`
433.7 mm (0.53–0.90 px across ±0.5 mm of plane; the mat plane 430.56 mm gives
1.5–1.9 px, which is the same failure that motivated Block 4's `marker_z_m`
change, now measured in sim).

The plan was regenerated against this calibration. **This is the single most
important result of the block**: the earlier "sim passes, bench does not" family
of failures had a measurable geometric cause, and the plan/scoring chain is now
consistent end to end.
