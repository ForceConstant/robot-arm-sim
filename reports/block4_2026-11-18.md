**Code fix (production):** `chess_sim/marker_scan.py::observe_markers` iterated
the global `MARKER_IDS` (0–36, widened for the ChArUco face) and asked the
*layout* to describe each one, so a mat layout raised `unknown marker id 5` and
took the whole scan down. It now skips ids the layout cannot describe — exactly
what `fiducials.object_points` was already doing, for the same reason.

**Test fixes (test-only):** two assertions encoded the pre-ChArUco invariant
`len(points) == 4 * len(MARKER_IDS)` / `sorted(found) == [0,1,2,3]`. They now
assert what a *layout* defines (`GEOM_MARKER_IDS`, ids 0–4 including the loose
centre tag). No blanket xfail, no skipped test.

**The four plan tests (not fixed — precise reason):** `MarkerScanPlan` has no
marker set of its own. `views_per_marker()` keys on the global `MARKER_IDS`, so
`complete()` and `missing()` demand coverage of all 37 ids. A mat plan covering
0–4 can never be complete, and the committed ChArUco-era plan (which still
carries mat ids) is reported missing 0–4. Making this correct means giving the
plan an explicit expected-id set (or letting `complete()` take the layout) — a
production semantics change the live `/scan` gate reads. That is a planner
decision, not bench-time work.

**`test_hand_eye.py` (not fixed):** now runs against the sim calibration and a
piece pack it discovers itself, then fails at `len(observations) >= 6` because
`tools/solve_hand_eye.calibration_views` renders from a fixed posture against
the mat layout that, in the current scene, sees at most one marker per view
(§3b, same mat-geometry defect). Left visible rather than skipped over.

## 4. Dry-run harness

One command, offline, production solver, real limits, no motion:

```fish
~/.local/bin/robot-arm-sim python tools/block4_dryrun.py \
  --squares a1,b1,f1,g1,h1,a2,g2,g3
```

It runs `solve_tip` (the exact call `/move` makes) with `ArmKinematics.limits`
set from the bridge, plus an **unconstrained** probe of the same target so a
failure is attributable instead of mysterious.

Verdicts:

| verdict | meaning |
|---|---|
| `OK` | inside 20 mm / 8°, every joint inside the bridge range, tip inside keep-in |
| `IK_FAILURE` | unconstrained also misses → solver/target problem, not a limit |
| `JOINT_LIMIT` | unconstrained solves but needs a joint past the bridge range; the output names the joint, the required angle, the limit and the overshoot |
| `KEEP_IN_REFUSAL` | joints legal, tip leaves the ±118 mm / z −5…320 box |
| `RESCUED_BY_SEED` | with `--rescue`, a bounded random-seed search found a passing pose |

Result on the 8 flagged squares (a1, b1, f1, g1, h1, a2, g2, g3):

```
 a1  OK  3.9 mm 0.02°  wrist_flex (+36.8)     h1  OK  2.9 mm 0.17°  wrist_flex (+38.1)
 b1  OK  2.4 mm 0.19°  elbow_flex (+28.4)     a2  OK  0.9 mm 0.37°  wrist_flex (+37.2)
 f1  OK  3.7 mm 0.10°  elbow_flex (+25.7)     g2  OK  3.0 mm 0.16°  wrist_flex (+38.1)
 g1  OK  3.9 mm 0.42°  elbow_flex (+31.6)     g3  OK  3.0 mm 0.48°  wrist_flex (+39.0)
```

`reports/block4_dryrun.json`. Exits 1 if any square is not `OK`, so it can gate
a script; the reason is in the row either way.

At the production hover (60 mm) all 8 squares — and all 64 in the sweep — are
`OK`, so the refusal branches are correct by construction but **unexercised by
the bench run**. They fire on the same conditions the live app enforces
(`violations()` against the bridge limits, `_keep_in_check` on the tip), which
is why the harness is a pre-flight and not a second controller.

**`bridge fault` is a live-only category** and the harness cannot produce it by
construction (nothing is sent). On the live path it is any `/move` HTTP error
that is *not* `no reachable pose:` or `keep-in zone:` — a 409 from the bridge,
a timeout, `bridge left REMOTE during motion`. That mapping is step 11 of the
run sheet.

### The live `dry_run` path (documented for Block 5)

```fish
curl -s -X POST http://127.0.0.1:8080/move -H 'Content-Type: application/json' \
  -d '{"mode":"xyz","x_mm":-98.0,"y_mm":-98.0,"z_mm":60.0,"dry_run":true}'
```

- requires the bridge in **REMOTE and armed** — `/move` raises
  `bridge must be REMOTE and armed` otherwise (nothing about `dry_run` bypasses
  that check);
- returns `{"dry_run":true,"requested":{…},"target_joints":{…},
  "max_joint_delta_deg":N}` and sends no command;
- **it does not run the keep-in check** — `dry_run` returns before
  `_keep_in_check`, so a dry run can pass on a target the real move then
  refuses. Read `target_joints` against the limit table, don't read the 200.

## 5. Blocker found: the scan plan does not match the printed face

`live_config.json` pairs `"layout_kind": "charuco"` with
`"plan": "chess_sim/assets/marker_scan_plan.json"`. That plan is the **mat-tag**
plan (`layout_offset_mm: 152`, markers 0–3, tags 40 mm outside the board edge).
Every committed variant (`marker_scan_plan_50mm.json`,
`marker_scan_plan_tight.json`) is mat-based, and `tools/plan_marker_scan.py`
still hard-codes `fiducials.MarkerLayout.for_board(...)` with no ChArUco option.

With the ChArUco face, those poses point the wrist past the board: in sim, plan
pose 1 sees 4 ChArUco tags and poses 2–11 see none (`probe_plan`). `/scan` at
the bench would therefore fail registration on most views — the exact "no
markers" failure that reads like a hardware fault.

**This gates Block 5 step 7.** It is a pre-bench code task (generate a ChArUco
plan against `CharucoLayout`), recorded as step 0b of the run sheet with an
abort, so nobody improvises it at the arm.
