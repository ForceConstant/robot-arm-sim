# Phase 2 IRL gate — measured, failed on a loop ramp below the servo deadband (2026-11-24)

**Outcome in one line:** the arm actuates and the mink/3.0 console solves and passes
every pre-move check, but the real gate **FAILS** because `_stream_to` re-derives its
command from the *measured* pose every tick with a **0.693°** step, which is below the
servos' **2–4.4°** directional deadband — so the goal never leads and a loaded joint
does not move. The flip is **NOT applied**. Nothing committed.

This is a second, independent software cause from the torque bug fixed in `23338dc`
(that one is confirmed fixed: the arm moves, and the same joint moved 38° when commanded
to an absolute target).

## 4. Cause — the loop's ramp is below the servo deadband

`live/app.py:1448` and `:1485`:

```python
step = 10.5 * 0.066                       # 0.693 deg per tick
current = [m + max(-step, min(step, t - m))
           for m, t in zip(measured, target)]
```

Every tick recomputes from the **measured** pose and asks for at most 0.693° of lead.
The servos ignore sub-deadband goal changes (measured 2–4.4°, directional), so a
stalled joint never accumulates lead; the next tick re-reads the same frozen pose and
asks for the same 0.693°. Over 331 commands that is the observed 0.00° of lift travel.

The bridge cannot rescue it. `live/pi_bridge/app.py:749-765` deliberately ramps against
the **last commanded goal** ("a servo ignores sub-deadband steps, so anchoring on
measurement can stall a 0.2 deg/cycle ramp forever") and allows the goal to lead the
measurement by up to `MAX_LAG_DEG` (12°). But the *request itself* never exceeds
measured + 0.693°, so the bridge has nothing to ramp toward. `apply_target` would let
the goal advance 35 × 0.3 / 30 = **0.35°/cycle** toward a real request — plenty, if the
request led.

**Reproduced without the arm** (`--sim --deadband 2.5`, BC-250):

```
{"case": "park_at_start", "ok": false,
 "movement": {"per_joint_deg": [0,0,0,0,0,0], "travel_deg": 0.0}}
start pose not reached; the relocation case cannot mean anything  -> FAIL
```

0.000° on every joint, exactly the IRL signature. Same suite with `--deadband 0` passes,
so the only changed variable is the deadband.

**And the inverse is proven on the arm:** restoring the pose with absolute-target
commands (the owner's documented method) moved shoulder_lift **25.36 → −13.02°** in one
leg, seconds after the console's loop had moved it 0.00° for 30 s.

## 7. Two deployment facts the next attempt must not miss

1. **`ROBOT_GRIPPER=cad_parallel` + `ROBOT_GRIPPER_ASSETS`** are required for mink
   (`chess_sim.gripper` falls back to `stock` without them, and the first solve raises
   `KeyError: moving_jaw_so101_v1`). Verified both ways on the BC-250. They must land in
   `scripts/start-live.sh` together with the flip.
2. **The BC-250 tree does not contain `2970ec7`.** `live/app.py` there still has
   `recovery_joints.wrist_roll = 87.74`; the local repo has 0.0. The two files differ by
   that one line and nothing else. Until the deployed tree gets it, any auto-recovery
   will rotate the wrist ~88° to the old pose — which is what happened here. Not edited
   here, because the tree is the owner's in-flight work.

## 8. Proposed fix (NOT applied — needs a decision)

1. **Make the request lead the measurement.** Either command `target` directly (the
   bridge's `apply_target` + `MAX_LAG_DEG` already bound speed and lag), or advance
   `current` from the last *commanded* goal rather than from `measured`. The bridge's
   own comment at `pi_bridge/app.py:749-751` assumes exactly this.
2. **Stop condition must tolerate the deadband.** A 0.7° tolerance against a 2–4.4°
   deadband can never be met, so every move runs its full 30 s and reports ~3°; pair (1)
   with a settle tolerance ≥ the measured deadband, and report the residual honestly.
3. **Make the non-execution guard per-joint.** `needed`/`travel` as a max over joints
   lets a pan mask a stalled lift (this run's park case).

None of these is a flip-bundle item; each changes motion policy and deserves its own
sim (with `--deadband`) + IRL gate.
